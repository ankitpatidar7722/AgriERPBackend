# Dual database: SQL Server **and** PostgreSQL

AgriERP runs on either **SQL Server** (the original) or **PostgreSQL** from the same
codebase. You choose per deployment; nothing in the application layer changes.

Why PostgreSQL was added: its free hosting tiers (Neon, Supabase, Render, Railway)
are far more generous than SQL Server's, which matters when the goal is to run the
shop on free/low-cost infrastructure. The SQL Server path is untouched and fully
supported.

---

## 1. Choosing the provider

`appsettings.json` → `Database:Provider`:

```jsonc
"Database": { "Provider": "SqlServer" },   // or "PostgreSQL"
"ConnectionStrings": { "AgriERP": "<a connection string for that provider>" }
```

Default is **SqlServer**, so existing deployments keep working with no change.
`AddPersistence` reads the setting and wires `UseSqlServer` or `UseNpgsql`
accordingly (`AgriERP.Persistence/DependencyInjection.cs`).

Connection string examples:

```
# SQL Server
Data Source=SERVER\INSTANCE;Initial Catalog=AgriERP;User ID=...;Password=...;Encrypt=True;TrustServerCertificate=True

# PostgreSQL (Npgsql)
Host=localhost;Port=5432;Database=agrierp;Username=postgres;Password=postgres
# Neon/Supabase: Host=...;Database=...;Username=...;Password=...;SSL Mode=Require;Trust Server Certificate=true
```

## 2. The two schema sources

- **SQL Server** — `database/scripts/` (numbered `00`…`34`). The source of truth for
  SQL Server; run in order as before.
- **PostgreSQL** — `database/postgres/`. A hand-written parallel that produces the
  **final** schema directly (it does not replay the SQL Server migration history).

Both are kept in step with the EF model; the model is provider-aware
(`Configurations/ProviderModel.cs` + `ColumnShapes`).

### Build the PostgreSQL database

One command (drops the schema, runs everything in order, seeds):

```powershell
cd Backend/database/postgres
./build-postgres.ps1                 # into 'agrierp' with seed data
./build-postgres.ps1 -NoSeed         # schema only (what the integration tests expect)
```

Or by hand, in this order:

```
02_security 03_masters 04_items 05_inventory 06_purchase 07_sales 08_finance 09_system
80_foreign_keys 85_views 11_functions 12_seed_data
```

`README.md` in that folder documents the T-SQL → PostgreSQL translation rules.

### What each file is

| File | Contents |
|---|---|
| `02`…`09` | 56 tables (columns, PKs, checks, generated columns, indexes) — **no** inline FKs |
| `80_foreign_keys.sql` | all 103 foreign keys (deferred so table order never matters) |
| `85_views.sql` | 17 views (10 EF-mapped read models + 7 report views) |
| `11_functions.sql` | 4 PL/pgSQL functions (see §4) |
| `12_seed_data.sql` | reference data the app cannot start without (idempotent) |

## 3. Key schema differences (already handled)

| Concern | SQL Server | PostgreSQL |
|---|---|---|
| Identifiers | `[Name]`, case-insensitive | `"Name"`, quoted PascalCase to match EF |
| Optimistic concurrency | `ROWVERSION` column | system `xmin` column (`HasRowVersionConcurrency`) |
| Timestamps | `datetime2(3)` | `timestamp(3)` |
| Persisted computed cols | `AS (expr) PERSISTED` | `GENERATED ALWAYS AS (expr) STORED` |
| Filtered unique indexes | `WHERE [IsDeleted] = 0` | partial index `WHERE "IsDeleted" = false` |
| Single-NULL unique | default | `NULLS NOT DISTINCT` where needed |
| Identity | `IDENTITY(1,1)` | `GENERATED BY DEFAULT AS IDENTITY` |

`RowVersion` is never read on the client, so using `xmin` on PostgreSQL is invisible
to the frontend.

## 4. Stored procedures → PL/pgSQL functions

The four routines the app calls have PostgreSQL equivalents in `11_functions.sql`,
and the three services that call them (`DocumentNumberService`,
`StockPostingService`, `DashboardService`) branch on the provider
(`_context.Database.IsNpgsql()`), keeping the SQL Server path byte-for-byte
original:

| SQL Server | PostgreSQL | Notes |
|---|---|---|
| `usp_GetNextDocumentNumber` | `fn_get_next_document_number` | one atomic `UPDATE … RETURNING` |
| `usp_PostStockTransaction` | `fn_post_stock_transaction` | `SELECT … FOR UPDATE` = `UPDLOCK` |
| `usp_ReverseDocumentStock` | `fn_reverse_document_stock` | one data-modifying CTE |
| `usp_DashboardSummary` | `fn_dashboard_summary` | six `refcursor`s FETCHed in a transaction |

**Insufficient-stock** is raised as SQL error `50024` on SQL Server and SQLSTATE
`AG024` on PostgreSQL; both are mapped to a `BusinessRuleException`
("INSUFFICIENT_STOCK"). `ExceptionHandlingMiddleware` maps unique/FK violations on
both providers too.

`usp_GetAvailableBatches` and `usp_RebuildBatchQuantities` are **not** ported — the
application never calls them.

## 5. First run / seeding

1. Build the schema **with seed**: `./build-postgres.ps1`.
2. Start the API pointing at PostgreSQL. `DatabaseSeeder` (unchanged, pure EF) sets
   the admin password to `Admin@123` with `MustChangePassword` on first run.
3. Log in as `admin` / `Admin@123` and change the password.

The seed loads roles, permissions, the admin user, states, units, tax slabs, HSN
codes, item groups, transaction types, vouchers, number series, the active financial
year and settings. It does **not** load suppliers, customers, products or stock —
that is your shop's data.

## 6. Tests

All in `tests/AgriERP.Persistence.Tests` (they no-op if PostgreSQL is unreachable):

- `ModelBuildsForBothProvidersTests` — the EF model builds for both providers (offline).
- `PostgresConformanceTests` — EF queries every mapped table/view on `agrierp`
  (schema-only DB); catches any drift between the model and the hand-written schema.
- `PostgresServicesTests` — numbering, stock posting, reversal, the dashboard and the
  insufficient-stock path, all through EF + the PL/pgSQL functions, inside a
  rolled-back transaction.

Run them: `dotnet test --filter "FullyQualifiedName~Postgres"` (needs a schema-only
`agrierp`: `./build-postgres.ps1 -NoSeed`).
